# Big Boys Website Replacement Plan

## Correct delivery model

The local/GitHub codebase we built is the implementation target. The client's current Lovable website is only the approved visual and functional benchmark. We will improve this repository and deploy it as the replacement production site. Nothing will be built or published through Lovable.

## Phase 1: Freeze the benchmark

Capture the client site at desktop and mobile sizes, including the homepage, navigation states, representative service and location pages, blog, quote journey, and admin entry. Record typography, colors, spacing, card treatments, section order, CTA placement, and interaction behavior.

At the same time, record the current deployed replacement candidate, repository commit, environment variable names, routes, integration endpoints, quote steps, pricing behavior, form destinations, and console/build state.

Outcome: a visual benchmark, functional baseline, protected-file manifest, and rollback point.

## Phase 2: Map rather than redesign

Create a page map showing how each benchmark section is represented in this codebase. Reuse existing components and styling tokens. Identify only the missing elements: service discovery, service areas, authentic photos, social proof placement, FAQs, content depth, blog coverage, metadata, and mobile corrections.

Outcome: a scoped changed-file list with no unrelated redesign work.

## Phase 3: Build the complete customer journey

Correct desktop and mobile navigation first so every service, service area, blog, contact, phone, and quote path is reachable. Preserve the benchmark header and menu appearance. Then place authentic client photos where they provide the strongest proof and optimize them for responsive performance.

Outcome: discoverable architecture and an approved image-placement map.

## Phase 4: Build search value into the same design

Correct H1s, titles, descriptions, canonicals, social metadata, schemas, sitemap, and internal linking. Expand all 10 service pages and 16 city pages inside the established templates. Prevent thin city pages with useful verified coverage details rather than city-name substitutions.

Outcome: complete service and location coverage without doorway pages or a visual redesign.

## Phase 5: Answer objections and demonstrate trust

Use verified reviews only. Place compact proof early and fuller proof later. Expand FAQs around the real reasons customers hesitate. Publish eight interconnected, useful articles that support decisions, preparation, pricing understanding, and service discovery.

Outcome: stronger trust and content depth while keeping the benchmark component language.

## Phase 6: Protect the money path

Regression-test both quote methods, pricing/catalog loading, mobile viewport fit, step focus, booking, callback, leads, admin access, and tracking. Make usability fixes without changing calculations, fields, data sources, or destinations.

Outcome: the same working business system with a clearer mobile experience.

## Phase 7: Replace safely

Build and test the repository, deploy it to a preview on the current hosting platform, and visually compare it against the client benchmark at matching widths. Obtain approval, then deploy the same verified commit to the existing production project and domain. Preserve the previous deployment and commit for rollback.

Outcome: the improved repository replaces the current site without involving Lovable or disconnecting production integrations.

## Client verification before launch

- Confirm service boundaries, phone, email, hours, and availability claims.
- Confirm reviews, rating totals, and permission to publish them.
- Confirm insurance, background-check, donation, recycling, and guarantee language.
- Confirm every client photo is approved and does not expose faces, plates, addresses, documents, or private belongings unintentionally.
- Confirm displayed prices match the live catalog.
- Approve desktop and mobile preview comparisons.

## Definition of done

The replacement is complete only when it matches the client-approved design, runs from this codebase, preserves all verified integrations and business behavior, contains the expanded photo/SEO/service/location/FAQ/blog work, passes regression checks, is approved in preview, replaces the existing production deployment, and retains a tested rollback path.
